# 簡報風格：配色、版面與寫法

範本的實際值在 [`assets/deck-template/`](../assets/deck-template)（分層見 [patterns.md](patterns.md)「引擎分層」，宣告見 [declarations.md](declarations.md)）；本檔說明為什麼這樣用。字數上限與區塊欄位見 [patterns.md](patterns.md)。

## 版面骨架

外觀的載體是真正的 PPTX 範本（佈景主題、母片、版面；見 [patterns.md](patterns.md)「範本」）。下面是骨架的數值，都來自引擎的 `design.yml`。

16:9（13.333 × 7.50 in），白底。每張內容頁由上而下：章節標籤（11 pt，主色）→ 主標題（25.5 pt 粗體，寫結論句）→ 標題分隔線（1.56 in，把標題區與內容區分開）→ 內容區（上緣 1.70 in，下緣 6.85 in）→ 頁尾細線（7.00 in）→ 簡報短題與頁碼。單一區塊的頁面垂直置中；`note` 釘在底部。封面只有類別、題名、副題與作者（預設印作者，可用 `meta` 改寫），不放日期與機密字樣；日期放文件屬性。

## 色票語義

顏色只表示語義，一個意思一個顏色，全份簡報一致；Quarto 文件與簡報共用同一份 `_brand.yml`，意思才會一致。

| `kind` | 語義 | 何時用 |
| :--- | :--- | :--- |
| `blue` | 資料與結構 | 資料、系統元件、主流程；主色也用在封面細線、章節標籤與步驟序號 |
| `green` | 系統確定 | 由規則或系統確定的結果、通過驗證、已落實 |
| `amber` | 只給候選 | 系統只提供候選、待人確認 |
| `red` | 須人判斷或失敗 | 問題、攔截、風險、違規 |
| `gray`、`white` | 中性 | 說明、背景、預設 |
| `dark`、`solid_dark` | 墨色強調 | 出發點與收斂點，不帶語義 |

白底上的小字用語義色的 `-text` 深色版（對比 4.5 以上），線與填滿用主色，大面積底用 `-lite`。粗體段落放在綠色標題卡裡會改成墨色，保持可讀；語義儲存格（表格）保留語義字色。

## 幾何

卡片與節點圓角 3 pt，線寬 0.75（細線、分隔）／1.0（一般）／1.5（語義卡片）pt，不用陰影。連線一律直角，箭頭向終點；連線標籤的文字框透明。數值在 `design.yml` 的 `geometry`。

## 版式選擇

| 要說的事 | 用 |
| :--- | :--- |
| 先講完結論 | `steps` ＋ `banner`，或 `kpi` ＋ `note` |
| 問題與痛點 | `banner` ＋ `cards`（紅） |
| 系統怎麼接起來 | `arch-graph`（附 `note`） |
| 一件事的先後 | `flow`；跨角色用 `swimlane` |
| 狀態怎麼變 | `arch-graph`（節點＝狀態，邊＝轉換） |
| 方案怎麼比 | `table`（綠＝選它的理由，紅＝缺點） |
| 責任分界 | `layers` |
| 數字多大 | `kpi`（大數字，副說明寫來源與期間） |
| 數字怎麼變 | `chart`（原生圖表，寫明示例或實測、未驗證的部分） |
| 數字怎麼比 | `bench-chart`（長條加論證面板） |
| 何時做什麼 | `timeline-diagram` |
| 真的長什麼樣 | `shots`（實際截圖，附白話圖說） |
| 結論與風險 | `columns`（綠＝驗收、紅＝風險） |
| 換章與收尾 | `type: divider`、`type: closing` |

## 實際畫面

畫面一律用實際程式的截圖，不手繪示意，也不用 AI 生成的假畫面。用示範資料截（租戶、信箱、金鑰都是假的），視窗 1200×720、裝置像素比 2；扁長版面用 `crop` 取上緣，不另存裁好的圖。圖說用白話描述畫面在做什麼，截圖上改不了的字（選單、示範資料）不用解釋；替代文字用 `alt` 寫給看不到圖的人。畫面做不到的（例如需要外部服務才有的狀態）直接在頁面寫「本頁為未開啟某功能的狀態」，不補假圖。

## 白話命名

投影片與講稿備註不顯示倉庫名稱與代碼名稱（服務代號、端點與路徑、設定鍵、資料表與欄位、檔名）：讀者看不懂。改成白話的功能名稱，例如「平台服務」「營運後台」「證據接地服務」。學術與標準名詞（ISO/IEC 17788）與通用工具名（PostgreSQL、Kubernetes）讀者查得到，可以保留。給維護者的 README 與問答稿可以寫路徑。`scripts/lint.py` 擋 snake_case、檔名與路徑，專案專屬的倉庫與服務代號寫在 `lint.deny`（`deck.yml` 或任一層 `_quarto.yml`、`_metadata.yml`）或用 `--deny` 帶入，誤報放 `lint.allow`。

## 作者欄

作者照 Quarto 的分層中繼資料處理（細節見 [declarations.md](declarations.md)）：專案層寫一次，目錄層補人，`deck.yml` 不重複抄。給客戶與對外的說明通常不署名或署產品名，學位與內部報告署報告人；姓名與單位分兩個欄位（`name`、`affiliation`），不要擠進同一個字串，也不要另造「@鍵」之類的間接引用。

## 不標進度

簡報頁面與講稿只描述完成後的長相，不寫「規劃中」「目標流程」「尚未實作」「待核對」。程式現況、未定事項與待核對寫在該簡報的維護者文件，報告前由人核對。研究與評估報告的限制與未竟之處是研究內容，照寫，不屬於這一條。

## 講稿備註

鋪陳、背景與口頭引導寫進備註（每頁的 `notes`），投影片只留骨架、數據與圖形。備註同樣不寫代碼名稱；寫明數字出處與是實測、示例或估算。

## 驗證

1. `uv run deckstyle build deck/`：先驗證規格，再建置並自動跑零折行與白話命名檢查；有違規就改寫文字重跑。
2. `uv run <技能路徑>/scripts/lint.py out.pptx [--deny 倉庫名,服務代號]`：單獨檢查既有的 .pptx。
3. `uv run deckstyle preview deck/`（需 PowerPoint 與 poppler）或自己轉 PDF 與圖片，**逐頁**看：文字不溢出、不折行、不被截斷、不重疊；lint 以字寬估算，字型不同會有差異。
